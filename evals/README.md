# 触发词评测

`description` 是这两个 skill 里唯一常驻上下文的部分，它同时是**广告**和**路由规则**。写得太宽，用户问一句「这链接讲了什么」就白白拉进整套抓取流程；写得太窄，说「把这个存下来」却什么都不发生。

所以 description 的每次改动都当成行为改动对待：改完跑一遍 [`trigger-cases.json`](trigger-cases.json)，别凭感觉。

## 怎么跑

用例集本身是数据，没有 runner —— 触发与否由 agent 的路由决定，只能在真实会话里观察：

1. 开一个干净会话（两个 skill 都已安装，且没有其他会抢触发的 skill）。
2. 逐条发送 `query`，记录实际加载了哪些 skill。
3. 与 `expect` 比对。

## 判定

| 指标 | 目标 |
|---|---|
| `should_trigger`（`expect` 非空）命中率 | 100% |
| `should_not_trigger`（`expect` 为空）误触率 | 0% |

误触发比漏触发更贵：它会平白吃掉上下文，还可能真的去动用户的知识库。因此两者不达标时，**先修误触**。

不达标就回去改 description，不要改用例来迁就实现。新加一个站点适配或一个命令，顺手补一条对应用例；修好一次线上误触发，把那句原话补成用例。
